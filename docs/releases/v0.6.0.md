# v0.6.0 release notes — Combat MVP 1.0

Status: written ahead of the rehearsal so the driving developer can rehearse
exactly what will run in production. The rehearsal (on a copy of the
production `/data` volume) and the production run execute the same
[operator procedure](#operator-procedure) below.

Sources: the [Combat MVP 1.0 implementation
handoff](../spec/combat-mvp-1.0-handoff.md) (packages, gates and release
procedure) and [ADR 0009](../adr/0009-game-data-from-earlier-combat-rules-is-discarded-at-release.md)
(game data from earlier Combat rules is discarded at the v0.6.0 release).

Terminology: **MVP 1.0** is the Combat rules version
(`rulesVersion: simple-rpg-engine-stance-cards-1.0`). **v0.6.0** is the
application release that ships those rules. The project is still experimental;
this is not an application 1.0.

## What ships in v0.6.0

- Combat is fought under the MVP 1.0 stance, card and range rules through the
  shared command-panel UI (progressive enhancement: playable without
  JavaScript), in both the Arena and Scenario play.
- Five Scenarios ship in content format v2; the Encounter → initial Combat
  state builder, the v2 loader/validator and the winnability coverage come
  with them.
- Playthrough documents move to `schemaVersion` 3 and Arena runs to
  `schemaVersion` 1; the key `stateVersion` is never written again.

## Data discard — read this first

**All pre-v0.6.0 game data is discarded, not retired.** The release migration:

- deletes every Playthrough and every Journal entry;
- drops the `arena_runs` and `arena_setups` tables;
- keeps the `sessions` table (stays logged in, keeps nothing playable).

There are no retired Playthroughs, no "played under earlier rules" reason
code, and no frozen legacy Journal renderers. **Any campaign or Arena
progress from before v0.6.0 is gone after this release.** There is no way to
carry it forward and no way to get it back except the pre-release backup
used for rollback (see below).

**Scenario directory reset.** The release empties `/data/scenarios`
(`SCENARIO_DIR`) once, and the entrypoint re-seeds it with the bundled v2
collection. The shipped Scenarios on the production volume are format v1,
which the v2 loader rejects, so the reset is mandatory. The driving developer
confirmed there are no hand edits on the volume to keep: nothing in that
directory survives the release.

## Operator procedure

Executed by the operator after the deployment authorization; rehearsed first
on a copy of the production `/data` volume taken from host `rum`. Only the
driving developer pushes the `v0.6.0` tag, and no agent pushes a release tag.

1. **Stop the running container** so nothing writes. Never run two writing
   processes against the volume.
2. **Back up the whole `/data` volume** — the SQLite file
   (`DATABASE_PATH=/data/data.sqlite`) and `/data/scenarios` — consistently,
   off the host, and keep it until v0.6.0 is accepted in production.
3. **Empty `/data/scenarios`** so the new entrypoint re-seeds the bundled v2
   collection.
4. **Deploy: the driving developer pushes the `v0.6.0` tag.** `release.yml`
   runs the test gate, then `deploy.yml` builds the image on host `rum` and
   runs `compose -f compose.prod.yaml up -d --wait`. The container runs the
   wipe migration on start.
5. **Smoke-test:**
   - start a Playthrough in a converted Scenario and play one Round;
   - open the Journal in both languages (English and Polish);
   - start an Arena fight from a preset, import it and export it;
   - check the logs for loader diagnostics and rejected actions;
   - old browser tabs from before the release get a not-found or stale
     result, never a crash.
6. **Rollback (restore-then-redeploy):** stop the container, restore the
   step-2 backup to the volume, then run `deploy.yml` by `workflow_dispatch`
   with `tag: v0.5.0`. Redeploying the previous tag without restoring the
   backup does **not** work: the old image runs `npm run migrate` on start
   and Kysely refuses a database that a newer migration has already touched,
   so the previous image would not start.

**Everything played after the release is lost on rollback.** Restoring the
backup discards all v0.6.0 progress. A forward fix is the alternative when
the data since the release matters.
